# Лабораторный стенд ElXray

Только синтетические данные и отдельный тестовый UUID. HTTP/API остаются на loopback. Обычный TCP-стенд не требует TUN или VPS.

## Один ПК

Соберите `elxray.exe`, затем запустите `python3 testing/subscriptionrate/local_smoke.py --xray .\elxray.exe`. Скрипт управляет своими процессами и проверяет API и скорости. Старые процессы на лабораторных портах необходимо остановить заранее.

Для ручных измерений запустите в отдельных терминалах:

```powershell
python3 testing/subscriptionrate/http_bench.py --port 18080
.\elxray.exe run -config testing/subscriptionrate/node.example.json
.\elxray.exe run -config testing/subscriptionrate/client.example.json
```

В четвёртом терминале:

```powershell
python3 testing/subscriptionrate/bench_client.py --connections 2 --bytes 67108864 --direction both
```

Ожидаются суммарные 10 Мбит/с download и 5 Мбит/с upload. Разные доли отдельных потоков допустимы. Измеряйте общее окно счётчиков, пока все передачи активны:

```powershell
python3 testing/subscriptionrate/stats_window.py --xray .\elxray.exe --seconds 30
```

Прогрев 5 секунд, затем три окна по 30 секунд. Для строгой приёмки ориентир 90–110% номинала при достаточной полосе; недогруз CPU/сети или завершение участника делает результат неопределённым. Не сбрасывайте counters в процессе измерения. Меняйте скорости через API во время передачи: существующие TCP-потоки должны использовать новый бюджет без рестарта.

## Два ПК в одной LAN

ПК A запускает HTTP fixture и сервер. На обоих ПК работают клиентские ядра и benchmark. Скопируйте конфиги вне checkout, замените UUID на новый тестовый UUID в сервере и обоих клиентах.

У серверного VLESS inbound поменяйте listen на LAN IPv4 A. У клиентов settings.address укажите тот же IP. API/HTTP и клиентский SOCKS остаются loopback. Firewall открывает только TCP 24443 для Private/LocalSubnet; проброс роутера не нужен. Plaintext VLESS-пример используется только в доверенной лабораторной сети с синтетическими данными.

Одновременно запустите по одному потоку на A и B. На A снимите общее окно counters: общий потолок остаётся 10 down / 5 up, не по столько каждому. Повторите upload, оба направления, смену лимита и отключение B. После отключения B оставшаяся передача должна получить освободившуюся полосу. Это проверка общего бюджета, не подсчёта физических устройств.

## Режим TUN

`--mode tun` **не создаёт TUN-интерфейс**. Он открывает системное TCP-соединение к виртуальной тестовой цели `198.18.0.1:18080`, не используя SOCKS или fallback. Без работающего TUN и подходящего маршрута timeout ожидаем и не доказывает неисправность ядра.

Для такого стенда нужны: существующий TUN-клиент с маршрутом 198.18.0.1/32 через тестовый сервер, серверный `node.tun.example.json` и HTTP fixture на loopback сервера. Адрес сервера и loopback должны обходить TUN во избежание петли. Виртуальную цель не назначают реальному интерфейсу или роутеру.

```powershell
python3 testing/subscriptionrate/bench_client.py --mode tun --connections 2 --bytes 67108864 --direction both
```

Отключение сервера должно делать тестовую цель недоступной. Этот HTTP/TCP сценарий не проверяет DNS, IPv6, UDP/QUIC, MTU и kill switch. JSON ядра сам по себе не устанавливает ОС-драйвер TUN.
