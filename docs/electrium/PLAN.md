# План разработки Electrium Xray

## Зафиксированные требования

- Поддерживается собственный клиент.
- Один общий VPN-ключ/UUID на аккаунт. Дополнительная идентификация устройства не заменяет этот ключ.
- Первоначально ограничиваем суммарную скорость подписки в пределах одной ноды: одна нода — один экземпляр Xray.
- Загрузка и отдача ограничиваются независимо; параллельные соединения и разные профили не умножают бюджет.
- Активные устройства определяются по серверным сессиям, не по количеству IP и не по обращениям за подпиской.
- WebRTC и другие обходные транспорты работают отдельными адаптерами. Они не встраиваются в ядро Xray на этом этапе.
- 3X-UI пока остаётся upstream-панелью, собственные политики хранит backend.

## Этап 1. Ограничение скорости на ноде

- [x] Проверить исходную базу и пути Dispatch/getLink, DispatchLink/WrapLink.
- [x] Добавить группы подписок с привязкой к аутентифицированным email Xray.
- [x] Разделить общий бюджет uplink/downlink; 0 означает отсутствие ограничения.
- [x] Обернуть передачу данных в обоих путях диспетчеризации.
- [x] Запретить обход ограничителя через raw socket splice для ограниченной записи.
- [x] Добавить тесты агрегации, отмены ожидания, больших буферов, границ UDP и конфигурации.
- [x] Проверить граничные случаи безопасности, добавить fuzz/stress и сетевой loopback-тест VLESS; описать методику на одном/двух устройствах.
- [ ] Провести сетевой стенд VLESS+REALITY+Vision, TCP/UDP/XUDP и mux, измерить скорость и CPU.
- [ ] Проверить сборки и поведение на целевых ОС/архитектурах.

Текущая реализация задаёт лимиты через JSON при запуске. Управление без перезапуска относится к этапу 2. Код до завершения стендовых проверок не считать готовым к эксплуатации.

## Этап 2. Управление политиками без перезапуска

- Добавить закрытый API ноды для получения и атомарного обновления политик по subscription ID.
- Сохранять объект бюджета действующих соединений при смене скорости; не выдавать новый burst при каждом обновлении.
- Поддержать ограниченный → безлимитный → ограниченный режим для уже открытых соединений.
- Предусмотреть version/revision, повторную доставку, last-known-good и отказ при некорректном обновлении.
- Определить удаление подписки отдельно от снятия ограничения.
- Интегрировать агент и backend; FUP меняет серверную политику через этот API.

## Этап 3. Активные устройства и сессии

- Зафиксировать контракт account ID / device ID / session ID / node ID / transport.
- Спроектировать доказательство владения ключом устройства поверх общего VPN-ключа.
- Проверять допуск в ядре/шлюзе, чтобы общим UUID нельзя было обойти политику устройств.
- Атомарно выдавать и продлевать разрешения с ограниченным сроком действия.
- Определить правила переподключения, смены сети, смены транспорта и освобождения места.
- Поддержать принудительное завершение уже действующих сессий и отзыв устройства.
- Определить поведение при потере backend, перезапуске ноды и истечении разрешения.

Критерий: множество потоков одного устройства занимает одно место; третье устройство при лимите 2 не проходит даже через другую ноду. Глобальный учёт устройств и глобальное ограничение скорости — разные задачи.

## Этап 4. Наблюдаемость и 3X-UI

- Выдавать серверные события подключения/отключения и статистику по устройству, подписке и ноде.
- Разделять «подключено» и «сейчас передаёт данные».
- В кабинете показывать устройства, транспорт, время подключения, последнюю активность, скорость и объём.
- Добавить команды завершения сессии и отзыва устройства.
- Согласовать политику хранения IP и метаданных; не писать секреты и ключи в события.
- Связать backend с API 3X-UI, не хранить тарифную логику внутри патча ядра.

## Этап 5. Сменные транспорты

- Отдельно интегрировать whitelist-bypass для WB Stream/Телемоста и исследовать адаптеры OpenFlux, включая Yandex Board (WebSocket).
- Закреплять конкретные версии/коммиты зависимостей; обновления upstream проводить отдельными PR.
- Передавать через шлюз ту же идентичность подписки и разрешение устройства.
- Не допускать бесплатного выхода в Интернет до нашей авторизации.
- Решить первоначальный вход, когда обычный API кабинета недоступен.
- Проверить изоляцию пользователей, восстановление, доступность носителей и расход ресурсов.
- Проверить лицензии компонентов перед выбором способа их включения в клиент.

## Этап 6*. Общая скорость между нодами — отложено

Не реализуется в первом выпуске. В будущем сравнить распределение бюджета между нодами и закрепление сессии за нодой. Отдельно определить точность лимита, задержку обновлений и поведение при сетевом разделении. Не вводить удалённый запрос на каждый пакет.

## Работа с upstream и критерии выпуска

- Сохранять исходный module path Xray и небольшие тематические изменения.
- Готовить изменения в feature-ветках и PR; обновление upstream — отдельным PR.
- Проверять целевые пакеты, race detector, сборку бинарника и форматирование.
- Перед выпуском выполнять реальные тесты VLESS/REALITY/Vision, UDP/XUDP/mux, отключения и FUP.
- Публиковать сборки с точным commit SHA, описанием совместимости и возможностью отката.
