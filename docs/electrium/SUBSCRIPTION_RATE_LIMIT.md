# Ограничение скорости подписки: первый этап

Это расширение форка. Стандартный Xray и стандартный интерфейс 3X-UI не предоставляют описанные здесь настройки автоматически. Backend/агент должен сформировать эту часть конфигурации.

```json
{
  "policy": {
    "subscriptions": {
      "account-123": {
        "emails": ["account-123-vless", "account-123-trojan"],
        "uplinkBps": 1250000,
        "downlinkBps": 6250000
      }
    }
  }
}
```

Добавьте subscriptions в существующий policy, сохранив levels/system. Это фрагмент, не полный конфиг сервера.

## Семантика

- Ключ account-123 — стабильный ID подписки в нашем backend.
- emails — назначенные сервером email аутентифицированных пользователей Xray. При поиске политики регистр нормализуется так же, как в валидаторах VLESS/Trojan. Это не HTTP-заголовок клиента. Каждый email может находиться только в одной группе; повторы, включая разный регистр, отклоняются даже внутри группы.
- Все перечисленные email делят одну пару бюджетов, независимо от числа соединений, inbound и протоколов, проходящих через диспетчер Xray.
- Bps означает **байты в секунду**, не биты. Пример задаёт отдачу клиента 10 Мбит/с и загрузку клиента 50 Мбит/с. Пересчёт: Мбит/с × 1 000 000 / 8.
- 0 означает безлимитное направление. Пользователи, отсутствующие в subscriptions, сохраняют прежнее поведение.
- Максимальная допустимая скорость направления — 2^40 байт/с; отрицательные значения и дробные значения не соответствуют типу конфигурации.
- Лимит действует на полезные байты в диспетчере, без гарантии такого же потолка для сетевых заголовков, TLS, padding и транспортных повторов.
- Каждый бюджет начинается с burst 8192 байта. Это ограничение средней скорости с небольшим начальным запасом, а не точный потолок в каждом миллисекундном интервале.
- UDP-датаграммы сохраняют границы и метаданные. Они ожидают бюджет целиком; несколько соединений могут заранее оплатить пакеты и дать общий кратковременный всплеск. Это не жёсткое packet policing. Ограничение UDP может увеличивать задержку, поэтому нужен отдельный стенд.
- Одна нода должна использовать один экземпляр Xray. Несколько процессов/экземпляров имеют независимые бюджеты. Две ноды с лимитом 50 Мбит/с каждая могут суммарно передавать 100 Мбит/с — общий межнодовой лимит не предусмотрен.

## Обработка данных

Бюджеты принадлежат экземпляру policy manager. Все соединения подписки используют одни и те же объекты ограничителей. Учтены оба пути: Dispatch/getLink и DispatchLink/WrapLink, используемый VLESS.

Ограниченная запись требует буферного копирования: CopyRawConnIfExist не может перейти на splice, который обошёл бы её. На неограниченные записи это условие не распространяется. Снижение производительности ограниченного соединения относительно zero-copy нужно измерить.

Ожидание бюджета прерывается отменой контекста или Interrupt. Большие потоковые буферы разбиваются на порции, а пакетные границы сохраняются.

## Ограничения текущего этапа

- Настройки применяются при запуске/перезапуске ядра. Runtime API и FUP без перезапуска ещё не реализованы.
- Это не контроль числа устройств и не механизм отзыва сессий.
- Это не идентификация физического устройства по общему UUID.
- Отдельные процессы WebRTC/OpenFlux не получают этот лимит автоматически: их трафик должен проходить через авторизованный путь с общим бюджетом либо через будущую интеграцию.
- Полный стенд VLESS+REALITY+Vision, UDP/XUDP и mux остаётся обязательным перед эксплуатацией; модульные тесты его не заменяют.
