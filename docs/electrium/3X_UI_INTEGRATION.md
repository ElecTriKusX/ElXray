# Подключение нашей сборки к 3X-UI

## Как связаны проекты

Xray-Fork остаётся отдельным репозиторием ядра. 3X-UI управляет его процессом и конфигурацией. Копировать весь исходный код Xray внутрь панели или создавать повторный форк ядра не нужно.

Проверенные upstream-файлы 28 октября 2026:

- [internal/xray/process.go](https://github.com/MHSanaei/3x-ui/blob/main/internal/xray/process.go): GetBinaryName формирует имя xray-OS-ARCH, GetBinaryPath добавляет каталог бинарников панели, GetConfigPath указывает на config.json этого каталога. Не жёстко привязывать установщик к /usr/local: каталог зависит от конфигурации панели.
- [internal/web/service/xray.go](https://github.com/MHSanaei/3x-ui/blob/main/internal/web/service/xray.go): панель управляет экземпляром xray.Process.
- [go.mod](https://github.com/MHSanaei/3x-ui/blob/main/go.mod): панель также имеет зависимость от github.com/xtls/xray-core. Подмена исполняемого файла не меняет автоматически встроенные в панель Go-типы и её API-клиент.

Это проверка архитектуры upstream, не выполненная интеграция с конкретной установленной версией панели.

## Этап A: испытание готового ядра под панелью

1. Завершить локальный runtime API, регрессионные проверки, стенд REALITY/Vision и UDP/XUDP/mux.
2. Собрать нашу версию для ОС/архитектуры ноды и выпустить артефакт с SHA/версией/контрольной суммой.
3. На отдельном тестовом экземпляре панели сохранить её БД, конфиг и исходный бинарник, затем подключить нашу сборку по фактическому пути процесса.
4. Проверить запуск/остановку, генерацию конфигурации, StatsService и динамическое добавление штатных пользователей.
5. Проверить, что policy.subscriptions не пропадает после сохранения настроек, генерации конфигурации и перезапуска. Одной ручной правки сгенерированного config.json недостаточно.
6. Предусмотреть откат, а также обнаружение штатного ядра вместо нашей сборки. Автообновление не должно незаметно снять применяемые ограничения.

Штатные протоколы должны сохранять совместимость. Успешный запуск бинарника ещё не означает, что панель умеет управлять новыми функциями.

## Этап B: новые настройки и API

Первый вариант — собственный backend/агент хранит бизнес-политики и передаёт лимиты в закрытый API ядра. Панель остаётся близкой к upstream. Стартовая конфигурация должна содержать согласованную сохранённую политику, чтобы перезапуск не создавал unlimited-окно.

Если ограничения нужно редактировать непосредственно в интерфейсе 3X-UI, потребуется небольшой отдельный форк **панели**: поля/валидация, хранение, генератор конфигурации, клиент нашего API и проверка совместимой версии ядра. Это другая задача, не повторное форкание Xray.

При прямом использовании новых protobuf/API-типов в Go-коде панели её зависимость от Xray необходимо закрепить на совместимой версии нашего форка. Если агент работает отдельно, его SDK/схемы версионируются независимо. Этот выбор принимается при реализации интеграции.

## Критерии приёмки

- Изменение upload/download применяется к действующим соединениям без рестарта ядра.
- После рестарта панели/ноды ограничения восстанавливаются до допуска ограниченной подписки.
- Добавление/удаление пользователя не оставляет бесхозную unlimited-идентичность.
- Неверная версия ядра или отказ API заметны оператору; не сообщать об успешном применении неприменённой политики.
- Проверены обновление панели, обновление ядра и откат; штатная сборка не подменяет нашу молча.
- Административный API не публикуется в Интернет; тарифная логика не переносится в горячий путь передачи пакетов.
- Лимиты скорости применяются независимо внутри каждой ноды. Межнодовой синхронизации бюджета нет.
