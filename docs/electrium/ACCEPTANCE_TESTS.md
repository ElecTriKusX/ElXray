# Приёмка ядра: один ПК, два устройства, TUN

Результаты локального прогона: [VALIDATION.md](VALIDATION.md).

Поддерживаем только собственные клиенты. До появления нашего приложения Go/JSON-клиенты этого репозитория — лабораторные участники. Они не доказывают наличие проверки официального приложения или физических устройств.

## Один ПК: автоматическая проверка

Из корня репозитория, Windows PowerShell:

```powershell
go test -race ./common/subscriptionrate ./app/dispatcher ./app/policy ./app/policy/command ./common/buf ./proxy ./testing/subscriptionrate -count=1 -timeout 120s
go test -race ./infra/conf -run '^TestSubscription' -count=1 -timeout 90s
go test -race ./transport/internet/tls -run '^TestCertificateReloadConcurrentSelection$' -count=1 -timeout 30s
python3 -m unittest discover -s testing/subscriptionrate -p 'test_*.py' -v
go build -o xray-lab.exe ./main
python3 testing/subscriptionrate/local_smoke.py --xray .\xray-lab.exe
```

На Linux/macOS замените имя бинарника на `xray-lab`, путь на `./xray-lab`; при необходимости python3 на python. Для полного пакета infra/conf нужны geoip.dat/geosite.dat в resources; targeted TestSubscription не требует geodata. Полный `go vet ./infra/conf` может встретить исходный unreachable legacy reverse-код — это отдельная проблема базы.

Перед local_smoke остановите прежние лабораторные процессы на 1080/18080/24443/10085. Скрипт откажется при занятых портах. Он создаёт временный UUID/конфиги, поднимает только loopback HTTP + Xray server/client, проверяет одновременно download/upload 10/5 Мбит/с, API retry/conflict, смену на 5/2,5 Мбит/с, disabled и возврат unlimited. При завершении останавливает только свои процессы. Допуск автоматического smoke 70–115% номинала; при недогрузе ПК стенд надо повторить, верхнее превышение проверять как возможный обход. Для длительной приёмки используйте общие окна счётчиков ниже.

Сетевые Go-тесты отдельно проверяют:

| Тест | Что проверяет |
|---|---|
| TestSubscriptionVLESSSharedRate | TCP, 1/2 соединения, общая идентичность, оба направления, неверный UUID |
| TestSubscriptionMuxAndUDP | TCP mux, UDP, UDP mux, XUDP, два потока, сохранение пакетов, отдельные up/down бюджеты |
| TestSubscriptionVisionRuntime | TLS/REALITY + Vision, реальный внутренний TLS 1.3, включение лимита на двух уже открытых безлимитных потоках |
| TestSubscriptionRPC | Настоящий локальный gRPC: чтение, update, retry, conflict, обязательные поля |

Все адреса автоматических сетевых fixture — loopback; REALITY использует свой локальный TLS target, внешняя сеть не нужна. Это функциональная матрица, не исчерпывающая проверка всех сочетаний transport/flow/mux.

## Один ПК: ручное изменение во время передачи

Запустите HTTP, node.example.json и client.example.json по [WINDOWS_LAN_TESTING.md](WINDOWS_LAN_TESTING.md). Получите текущую revision. В клиентском терминале:

```powershell
python3 testing/subscriptionrate/bench_client.py --connections 2 --bytes 67108864 --direction both
```

На сервере во время передачи примените обновление из [RUNTIME_API.md](RUNTIME_API.md), уменьшая скорости вдвое. TCP-соединения не должны потребовать повторного установления. Измеряйте плато до/после, а не среднюю скорость всей смешанной передачи:

```powershell
python3 testing/subscriptionrate/stats_window.py --xray .\xray-lab.exe --seconds 30
```

Не сбрасывайте StatsService counters во время окна. Скрипт использует точный email lab@example и фактический интервал. Повторите limited → unlimited → limited, одну безлимитную сторону и disabled. После disabled передача должна оборваться/не начаться; остаток уже записанных данных допустим. Возврат disabled=false разрешает новые передачи, но не обещает восстановить уже закрытый TCP поток.

## Два устройства в одной LAN без VPS

ПК A запускает HTTP source/sink и серверный Xray. На A и B запускаются лабораторные клиенты с одним новым тестовым UUID и server-side email lab@example. Шаги адресации/Firewall — в [WINDOWS_LAN_TESTING.md](WINDOWS_LAN_TESTING.md). Меняется только VLESS listen на LAN-IP A и адрес сервера у клиентов; HTTP/API остаются loopback A. Проброс портов роутера не нужен.

На A и B одновременно запустите по одному `bench_client.py --bytes 67108864`. Пока обе передачи активны, снимите на A общее 30-секундное окно stats_window.py: downlink должен быть около 10 Мбит/с суммарно, не по 10 каждому. Затем повторите upload (около 5 суммарно) и both (одновременно 10 down + 5 up). Равенство долей A/B не является критерием.

Смените скорость через API, пока передают оба устройства. Обе передачи делят новое ограничение без рестарта Xray. Отключите B: A должен получить освободившуюся полосу. Измените только IP B в пределах сети: общий бюджет не должен удвоиться. Эти проверки не считаются контролем числа устройств: он ещё не реализован.

## TUN на одном или двух устройствах

Это сценарий для нашего клиента с реализованным TUN. Установка JSON в Xray сама по себе TUN-интерфейс не создаёт. В этом репозитории нет ОС-обвязки/драйвера TUN и WebRTC адаптеров, поэтому такой стенд пока нельзя объявить пройденным.

1. На A используйте `node.tun.example.json` вместо обычного node.example.json. Он направляет лабораторный TCP к loopback HTTP:18080; API/fixture остаются закрытыми для LAN. Для LAN меняйте VLESS listen и тестовый UUID как выше.
2. В нашем клиенте направьте `198.18.0.1/32` через TUN → наш VLESS сервер; задайте режим proxy для этой тестовой цели. Сам адрес сервера A, loopback и административный канал должны обходить TUN, чтобы не возникло петли. Не назначайте 198.18.0.1 реальному сетевому интерфейсу/роутеру — это виртуальная цель теста.
3. Из клиентского терминала запустите:

```powershell
python3 testing/subscriptionrate/bench_client.py --mode tun --connections 2 --bytes 67108864 --direction both
```

В этом режиме Python открывает обычное системное TCP-соединение к 198.18.0.1:18080, SOCKS не использует, HTTP_PROXY/NO_PROXY не читает. Такой запрос может перехватить TUN клиента. Если TUN/маршрут отсутствует, тест должен завершиться ошибкой.

4. Снимите counters на A, повторите изменение лимитов, отключение сервера и восстановление. При отключённом сервере тестовая цель не должна становиться доступной напрямую. Для двух устройств повторите команду на A и B с общим окном counters на A.
5. DNS, IPv6 и UDP/QUIC требуют отдельных endpoint/тестов; успех HTTP/TCP не засчитывает их. Проверьте в собственном клиенте выбранную DNS-политику, отсутствие обхода маршрута по IPv6, MTU, сон/пробуждение, смену Wi-Fi, повторное подключение и очистку маршрутов после остановки. Запишите ожидаемое поведение kill switch и проверьте его отдельно.

Не называйте серверную UDP-матрицу проверкой ОС TUN: она не проходит драйвер и маршруты конечного устройства.

## Критерии и протокол результата

Для ручной скоростной приёмки: прогрев 5 с, 3 общих окна по 30 с при непрерывной нагрузке. Цель — 90–110% полезной скорости при достаточной пропускной способности, без устойчивого превышения потолка. Недогруз, раннее завершение одного участника, сброс counters, Wi-Fi потери или узкий CPU делают результат неопределённым и требуют повторения.

Записывайте commit SHA ядра/клиента, ОС, transport/flow/mux/TUN, число потоков/устройств, обе скорости, revision, объём/целостность, CPU/RSS/FD, потери/задержки и результат. Проведите 30–60 минут нагрузки, многократные переподключения и несколько обновлений политики. Наши автоматические smoke не заменяют эту проверку.
