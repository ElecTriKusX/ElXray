# Проверка на одном устройстве и на паре устройств

**Для Windows PowerShell и домашней LAN сначала используйте [WINDOWS_LAN_TESTING.md](WINDOWS_LAN_TESTING.md).** Там есть Python runner без curl/Start-Job и команды без пустых shell-аргументов. Команды Bash ниже нельзя переводить в Windows PowerShell 5.1 только заменой curl на curl.exe.

## Что проверяем сейчас

Общий лимит подписки внутри одного экземпляра Xray, независимость uplink/downlink, параллельные соединения, целостность данных, отмену и сохранение обычной аутентификации.

Два соединения в автотесте моделируют два подключения с одним UUID. Они **не доказывают** идентификацию двух физических устройств. Контроль устройств и отзыв сессий ещё не реализованы. Runtime API скоростей реализован; автоматический FUP требует агента/панели. Общий лимит разных нод исключён из проекта. Третье подключение сейчас не обязано блокироваться.

## 1. Автоматические проверки

Из корня репозитория, с Go требуемой в go.mod версии:

```bash
go test -race ./app/dispatcher ./app/policy ./common/buf ./proxy ./infra/conf ./testing/subscriptionrate -count=1 -timeout 90s
go test ./app/dispatcher -run '^$' -fuzz '^FuzzRateChunksPreservePayload$' -fuzztime 30s -parallel 2
go vet ./app/dispatcher ./app/policy ./common/buf ./proxy ./testing/subscriptionrate
python3 -m unittest discover -s testing/subscriptionrate -p 'test_*.py' -v
go run ./infra/vformat/main.go -mode check -pwd ./
go build -o xray-lab ./main
```

Для тестов infra/conf нужны реальные resources/geoip.dat и resources/geosite.dat, как в upstream workflow scheduled-assets-update.yml. Не подменять их пустыми файлами. Общий `go vet ./infra/conf` отдельно сообщает уже существующий недостижимый код legacy reverse в infra/conf/xray.go; это не результат изменений лимитера.

Сетевой автотест `TestSubscriptionVLESSSharedRate` поднимает настоящие VLESS TCP-соединения на loopback, проверяет один и два потока с одним UUID отдельно для обоих направлений, целостность echo-ответа и отказ неизвестному UUID. REALITY/Vision и физические устройства этим тестом не проверяются. Race detector распространяется на исполняемый код тестового процесса, включая запущенное внутри него ядро.

## 2. Изолированный стенд для одного устройства

Нужны одна тестовая нода, один компьютер с SSH/curl/Python и собранные бинарники для соответствующих ОС/архитектур. Linux amd64 бинарник нельзя просто запускать на Android/iOS. На телефоне второй этап выполняется после появления нашего клиента с необходимым режимом; второй процесс на ПК заменяет только второе подключение.

Схема: curl → локальный SOCKS Xray-fixture → SSH local forwarding → отдельный VLESS на ноде → loopback HTTP source/sink. Клиентский Xray здесь является лабораторным инструментом, не поддерживаемым пользовательским приложением.

Не заменяйте рабочий бинарник, systemd unit, конфиг 3X-UI и рабочий UUID. Возьмите копии node.example.json/client.example.json. Замените демонстрационный UUID в обеих копиях одним случайным UUID (`python3 -c 'import uuid; print(uuid.uuid4())'`). Все три порта стенда — 24443, 10085 и 18080 — слушают только loopback. Если заняты, согласованно замените их в копиях и командах. Сам HTTP fixture не открывает файлы и не принимает произвольные назначения; один запрос ограничен 128 MiB.

На ноде, в двух терминалах:

```bash
python3 testing/subscriptionrate/http_bench.py --port 18080
./xray-lab run -test -config node.lab.json
./xray-lab run -config node.lab.json
```

В первом терминале остаётся HTTP-сервис; две команды Xray выполняются во втором. В node.lab.json уже разрешён только TCP 127.0.0.1:18080, остальной выход блокируется. Этот пример нельзя использовать как общий production outbound.

На тестовом компьютере, в разных терминалах:

```bash
ssh -N -o ExitOnForwardFailure=yes -L 127.0.0.1:24443:127.0.0.1:24443 USER@NODE
./xray-lab run -test -config client.lab.json
./xray-lab run -config client.lab.json
```

Сначала убедитесь, что SSH-туннель и клиент запущены. В примере VLESS без TLS идёт только внутри SSH; на открытый интерфейс такой inbound не переносить. Это проверка лимитера поверх VLESS, не проверка поведения DPI, REALITY или пропускной способности WB Stream.

## 3. Измерения с одного устройства

Пример задаёт download **10 Мбит/с** и upload **5 Мбит/с**. Bps в конфиге — байты/с: 1 250 000 и 625 000. Не путать MB/MiB и Мбит/с.

Сначала прогрейте соединение небольшим запросом:

```bash
curl --fail --noproxy "" --socks5-hostname 127.0.0.1:1080 'http://127.0.0.1:18080/download?bytes=1048576' -o /dev/null
```

`--noproxy ""` обязателен: NO_PROXY/localhost-исключения не должны отправить запрос напрямую на компьютер. Проверка пути: остановите локальный клиент и повторите запрос — он должен завершиться ошибкой, а не продолжить скачивание. После запуска клиента запрос снова должен работать.

Скачивание 64 MiB, повторить три раза:

```bash
curl --fail --silent --show-error --max-time 180 --noproxy "" --socks5-hostname 127.0.0.1:1080 'http://127.0.0.1:18080/download?bytes=67108864' -o /dev/null -w 'download_bytes=%{size_download} seconds=%{time_total} bytes_per_second=%{speed_download}\n'
```

Отдача 32 MiB, повторить три раза:

```bash
python3 -c 'open("upload.lab.bin", "wb").truncate(33554432)'
curl --fail --silent --show-error --max-time 180 --noproxy "" --socks5-hostname 127.0.0.1:1080 -H 'Expect:' --data-binary @upload.lab.bin 'http://127.0.0.1:18080/upload' -w 'upload_bytes=%{size_upload} seconds=%{time_total} bytes_per_second=%{speed_upload}\n'
```

Ответ upload должен содержать `received=33554432`. Приведённые shell-команды написаны для Bash. Для Windows используйте отдельную инструкцию, указанную в начале. Curl проверяет транспортные ошибки, но не криптографическую целостность большого потока: отдельно скачайте небольшой ответ в файл и проверьте его размер/нулевое содержимое. Автотест также сравнивает payload побайтно.

Пересчёт измерения: `Мбит/с = 8 × bytes_per_second / 1 000 000`. Сохраняйте все три результата, а не только лучший. Начальный burst 8192 байта заметен в очень коротком тесте; на 32–64 MiB он практически не меняет среднее.

Далее запустите 4–8 скачиваний одновременно в разных терминалах. Их **суммарная** скорость должна остаться около 10 Мбит/с. Последовательный запуск этого свойства не проверяет. Одновременно запустите download и upload: должны действовать независимые 10/5 Мбит/с, а не общий потолок 10 Мбит/с на оба направления.

## 4. Два устройства

На обоих устройствах запустите SSH-туннель и лабораторный клиент с **одним серверным UUID**. Каждое устройство использует свой локальный 1080; менять серверный email для второго устройства не нужно.

| Сценарий | Ожидаемый результат |
|---|---|
| A скачивает, B простаивает | A около 10 Мбит/с при достаточном канале |
| A и B скачивают одновременно | Общий потолок около 10 Мбит/с, а не 20 |
| Оба отдают данные | Общий потолок около 5 Мбит/с |
| A скачивает, B отдаёт | Независимые 10 и 5 Мбит/с |
| A использует 1 поток, B использует 8 | Потоки не умножают общий потолок; равные доли не гарантируются |
| B разрывает соединения и переподключается | Общий бюджет подписки не сбрасывается |
| Один UUID получает иной регистр серверного email при повторном стендовом запуске | Политика продолжает применяться |
| Неверный UUID | Нет доступа к HTTP fixture |
| Другая подписка с отдельным email/UUID | Имеет независимый бюджет при достаточной мощности канала |

Для двух устройств предпочтительнее измерять **на ноде по счётчику подписки**: время клиентов не нужно синхронизировать. Дайте обоим загрузкам работать непрерывно, снимите счётчики в начале и конце общего 30–60-секундного окна. Повторите 3 раза. Снимать на ноде:

```bash
./xray-lab api statsquery --server=127.0.0.1:10085 -pattern 'user>>>lab@example>>>traffic'
```

Не используйте `-reset`. Для каждого направления: `R = 8 × (counter_end − counter_start) / seconds / 1 000 000`. Убедитесь, что обе передачи активны всё окно; при необходимости увеличьте размер ответа до 128 MiB или начните следующую загрузку. Счётчики Xray включают полезную передачу его путей; цифры могут немного отличаться от HTTP body и сетевого интерфейса из-за разных точек учёта.

## 5. Критерии и отрицательные проверки

- Перед тестом установите оба лимита в 0 в копии конфигурации и перезапустите только стенд. Базовый канал, CPU и SSH должны обеспечивать не менее 2× заданной скорости. Иначе низкую скорость нельзя приписать лимитеру.
- На устойчивом TCP-нагруженном окне 30–60 с ориентир верхней границы — 105% лимита. Это лабораторный допуск, не математическая гарантия на любой короткий интервал. Нижний ориентир 80% применим только при подтверждённом запасе канала; иначе результат «неопределён», а не «лимит работает».
- При 0 в одном направлении оно должно вернуться к baseline, другое — остаться ограниченным. Перезапускайте только лабораторный экземпляр; действующие подключения при перезапуске разорвутся.
- Разорвите скачивание, затем повторите его 50 раз. Не должно оставаться зависших соединений. Снимите число потоков/FD и RSS до нагрузки, во время и через минуту после. Go может удерживать выделенную память, поэтому возврат RSS к исходному байту не требуется; проверяется отсутствие непрерывного роста между одинаковыми сериями.
- Приостановите устройство/SSH и восстановите сеть. Не должно появляться бесплатного выхода в обход ядра. Повторный вход не должен создавать новый бюджет внутри того же процесса.
- Проверьте пределы конфигурации отрицательными/дробными/слишком большими Bps и повтором email, включая разный регистр: конфиг должен быть отклонён до запуска.
- Не считать честным распределение 50/50 обязательным: сейчас реализован общий потолок, не планировщик справедливости между устройствами.

## 6. Отдельная проверка REALITY/Vision, UDP/XUDP и собственного клиента

После прохождения простого стенда повторите измерения на отдельном тестовом inbound с уже проверенными настройками REALITY/Vision проекта, без экспериментов с SNI. Не переносите plaintext-конфиг из этого документа на публичный интерфейс. Используйте наш клиент либо временный лабораторный Xray с тем же flow/streamSettings; повторите матрицу с одним и двумя устройствами, несколькими потоками, stats on/off.

UDP требует другого генератора: контролируемый iperf3 endpoint и TUN нашего клиента, чтобы UDP реально шёл через VPN. SOCKS/curl-стенд выше UDP не проверяет. Сначала измерьте baseline; затем UDP ниже лимита, на лимите и при 2× лимита, отдельно с двумя устройствами. Сохраняйте delivered bitrate, потери, jitter, задержку и размер датаграммы. Не приравнивайте задержку UDP к хорошей работе только потому, что средняя скорость ограничена. Клиентский маршрут до endpoint и рост счётчиков нужной подписки обязательны; простой speedtest без проверки пути может обойти туннель.

Физический тест «третье устройство не подключается», отзыв устройства и запрет чужого клиента добавляются после реализации серверных разрешений устройств. Два физических устройства не позволяют доказать ограничение третьего; дополнительный процесс тестирует только дополнительную сессию.
